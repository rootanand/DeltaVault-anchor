DeltaVault — a commitment root, and how to check it yourself

This is a demonstration, not a trust root. Every key below is derived from a fixed one-byte seed committed to a source repository, so anyone can reproduce them and nobody should trust them. A production DeltaVault root key is generated in a witnessed ceremony under dual control and has never existed on a laptop. Do not treat anything here as evidence of anything.

A commitment root was produced on a laptop. It is published here, with the proofs that connect a single record to it, and with a verifier you can read in five minutes that depends on none of our code.

Check it

The verifier needs Python 3 and OpenSSL and nothing else. It recomputes every digest with hashlib and checks every signature with the openssl command, so agreement means two independent implementations agree rather than that our code agrees with itself.

git clone https://github.com/rootanand/DeltaVault-anchor
cd DeltaVault-anchor
python3 verify.py

Read VERIFY.md for what each check establishes, and what it deliberately does not.

The files

  • root.json — the root file a verifier starts from
  • checkpoint.json — the commitment root, signed
  • batch.json — the batch commitment under it
  • record-inclusion.json — one record's proof into the batch root
  • checkpoint-membership.json — the batch root's proof into the checkpoint
  • log-head.json, log-inclusion.json, log-witness.json — the anchor log's signed head, the checkpoint's inclusion in it, and the log's own statement
  • verify.py — the third-party verifier

Every JSON file is in the DeltaVault canonical profile: keys sorted by UTF-8 byte value, integers as quoted decimal strings, no JSON numbers anywhere, and no trailing newline. That profile is what makes a digest reproducible in another language a decade from now, and verify.py reimplements it in four lines.
